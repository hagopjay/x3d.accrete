01 / Begin with one inspectable world

Open the laboratory.
Keep the terminal.

The local application stores its world in SQLite, serves its own browser interface and uses the bundled X_ITE runtime. A hosted account, room service and model API are not prerequisites for this reference edition.

Windows

Use the provided launcher.

Run run.bat, or start the server with py -3 serve.py --open. Open the local author link printed by the server. It carries a local write capability; the plain viewer address does not.

Keep the process running while exploring. A local write capability is not a signed-in person's identity.

WSL / Linux / macOS

Serve the same project.

Run bash run.sh, or python3 serve.py --open. The default viewer address is http://127.0.0.1:8820/; the printed author link adds the local write capability. The validator dependencies are pinned to lxml==6.1.1 and jsonschema==4.26.0; follow README.md for their bootstrap. The renderer is bundled; no model output is fetched.

The viewport needs WebGL. Check VALIDATION.md for the actual browser observations and any fallback behavior.

The first distinction: a seeded demonstration world shows what the authored generator can build. A new press of Grow appends a locally generated patch. Neither is a live model response, and neither measures the original private artifact.

The default demonstration starts with 24 authored seed entries. Read the current head and its source label. Press Grow once, inspect the newest ledger entry, and use Verify chain before changing another control. The point is to see the relationship between a proposal, its evidence and the place where it lands.

The generator proposes.
The planner places.
The admission profile checks.

The future hosted generator would occupy the proposal row, not the planner, validator or curator rows. Its output would still enter as untrusted generated material. The useful integration boundary is already testable without making that future call.

03 / Follow one append

A new layer is a transaction,
not a hopeful sequence of writes.

  1. Read and bind the planning context.The expected head and tail digest identify the history from which the next plan is derived. The planner owns its cell and layer.
  2. Generate a bounded proposal.The local authored recipe interprets its deterministic seed and selected tier. Preserve its source label and raw proposal identity.
  3. Normalize and inspect.The fragment gate rejects unsupported constructs, checks fields and references, computes its conservative envelope and applies the declared fit.
  4. Validate the actual wrapped candidate.The pinned XSD and semantic stages inspect the scene that will be admitted, including the normalization and fit wrapper. Their results bind to those bytes.
  5. Compare the current head inside a write transaction.If another append won the race, the stale request cannot attach its old plan to a new history. The caller must read and plan again.
  6. Commit the entry and its evidence together.Only a committed successor becomes visible to other readers. A hash, admission evidence, planned placement and payload belong to the same recorded action.

The SQLite boundary is a local storage contract. It avoids a shard/manifest half-write in this implementation; it does not prove a distributed database protocol. A later cloud adapter needs equivalent transactional comparison and explicit retry behavior, rather than assuming that a renewable lease alone prevents every race.

Why compare-and-swap matters: two clients can both plan from the same earlier head. The system must not accept both under a claim that each was the unique next layer. A stale-head conflict is a useful result, not an inconvenience to suppress.

04 / Read a pass at its actual scope

Local admission is useful.
It is not universal certification.

The local admission profile requires the fragment gate and the actual pinned XSD/semantic validator stages. The gate's result, the validator's results and the append decision have different jobs.

ObservationWhat a pass meansWhat remains separate
Fragment policyThe normalized fragment satisfies the supported language, field, reference and resource rules in this gate version.The rest of X3D, a browser's execution and visual quality.
Grammar / XSDThe wrapped X3D candidate satisfies the pinned schema checks that actually ran.Additional semantic constraints and runtime behavior.
Meaning / semanticsThe named validator's supported semantic checks found no blocking violation in those candidate bytes.Unsupported semantics, visibility, performance and human intent.
Local appendThe declared admission requirements passed and the current-head transaction accepted this successor.Acceptance of the entire app under an external Loom release profile.
Browser previewA person can inspect the current rendering under a named local runtime.A candidate-bound, camera-pinned render witness unless such an instrument actually records one.

The original design's “gate is a witness; ledger is a receipt” becomes more precise here. The world log uses its own application record. A formal loom.receipt/1 is an accepted-artifact record produced after the actual Loom kit checks a declared release profile. This application does not acquire that authority by using a similar JSON shape.

Valid is not visible. A fully transparent material, an unhelpful camera or an unsupported runtime path can defeat the intended experience without being the same failure as malformed XML. Keep behavior, eyes and host checks visible as unrun until they are measured.

When a required stage is unavailable or errors, it cannot silently become a pass. Read the difference among pass, fail, error and not_run. A validator crash is an instrument failure, not a successful rejection of a bad patch.

05 / Give motion room without losing containment

The slot must contain
the whole supported motion.

A static bounding box at time zero is insufficient for a moving patch. Translation can carry a shape away; scale can enlarge it; rotation can swing a long part beyond its original box. Nested transforms compound those effects. Even finite input numbers can overflow during composition.

Geometric policy

A conservative envelope.

The gate computes a supported whole-motion envelope, uses a deliberately safe bound where needed, and refuses unsupported combinations instead of pretending to certify them. The contract and diagnostic list live in docs/GATE-CONTRACT.md.

Visible transformation

Fit with a loss report.

The fit scale is part of the admitted candidate. Preserve the original extent and applied fit separately from the fitted extent. Scaling a proposal is an authored presentation operation, not evidence that the original proposal was already inside its slot.

The reference targets a bounded patch within the planner's world cell. Its resource policy is intentionally narrower than the full X3D standard. Rejecting Text, external resources, Script or global scene controls in this patch language is an application choice; it is not a claim that those X3D features are inherently invalid.

What a useful bounds test looks like.

Use a long box under a rotated transform, a nonuniform scale and an interpolated translation. Give it a repaired twin that stays inside the declared slot and a fault that crosses the limit. Require a specific diagnostic or a specific conservative fit, not merely “the test went red.” Add huge finite values and nonfinite products as separate controls. The expected result must name the state and interval that were inspected.

The browser remains a separate observation. A certified geometric envelope does not establish actual animation timing, GPU cost, light scope or the viewer's sense of motion. The bundled renderer version belongs beside any browser claim.

06 / Read the ledger as a chain of identities

History is more useful
when its transformations are named.

A growth step has several legitimate byte identities. Keep them distinct: the raw proposal; the normalized fragment; the fitted, wrapped X3D scene; the placement plan; and the complete append entry. Their hashes answer different questions.

IdentityQuestion it answersCommon mistake
Raw proposalWhat did the generator supply?Showing only the repaired result and losing the original failure.
Canonical fragmentWhat did normalization and name isolation produce?Reusing a raw-fragment pass after the bytes changed.
Wrapped candidateWhat exact X3D scene did the validator inspect and storage admit?Leaving the fit wrapper or required declarations outside the checked identity.
Instrument and policyWhich code, schemas, version and requirements produced the decision?Recording a repository name without the actual file hashes.
Append chainHow does this admitted step link to the previous retained head?Treating internal chain consistency as authenticated authorship.
A chain needs a point of comparison. Verification can detect drift relative to a retained head or checkpoint. An operator controlling an entire unsigned history can rewrite it and compute a different self-consistent chain. Exporting and retaining a checkpoint outside the database gives later comparison a concrete anchor; it is still not a signature.

The entry timestamp created_utc is inside the hashed payload, and verification requires the exported row timestamp to match it. This binds a recorded clock reading, not the accuracy of that clock. The sequence number defines append order. Timestamps and attempt identities influence later chain-derived seeds: identical initial settings in fresh databases do not promise identical worlds. Replay checks the recorded history and its inputs. The sequence and tail digest make a concise name for a historical world state. A verified checkpoint is useful for replay, sharing a study and reporting a fault. It does not prove that a named person or model generated the content.

Append-only is an application storage rule. The local database rejects ordinary entry edits through its declared path. The guide does not claim that the owner of a machine is physically unable to alter its files. State those scopes separately.

07 / Keep the local roles literal

A viewer is a session.
Authority is a different contract.

The plain local address is a viewer. The author link carries the local write capability generated by the server. Mutation authorization happens on the server, not because a button is visible or a browser says it is the owner.

This local capability is not a hosted account or proof of a distinct human. The reference does not reproduce the private artifact's authenticated room service, database rules or owner plan billing. It also does not infer that two tabs are two people.

Manual growth is deliberate.

Animation can continue while a world is viewed, but new world content is appended by the explicit growth action. This edition does not schedule paid calls or silently enable auto-growth.

The original “grow only while people watch” idea remains a meaningful future social rule. To implement it honestly, a hosted adapter must define authenticated identity, a heartbeat expiry window and what happens when presence changes during a build. Presence can permit creative activity; it must never replace write authorization or admission evidence.

Share the right thing: share a viewer address or an exported world for review. The author link is a write capability for that local server. The application is a local reference, not a production multi-tenant identity service.

08 / Explore the skyline without confusing the display

The world can keep its history
while the viewport keeps a budget.

The planner places new cells on a deterministic outward spiral and augments chosen cells with new layers. That gives the world a frontier and a skyline. Tier inputs change an authored structural ambition; they do not change the admission rules into a taste score.

Time

Inspect an earlier head.

The timeline is a view of a retained prefix of history. Moving it should change what is shown, not erase later entries or rewrite an earlier append. Return to the current head before planning new work.

Distance and scale

Read a proxy as a proxy.

LOD and proxy rendering are presentation strategies. A box summarizing an older patch is not that patch's full geometry. Its label should stay visible in the interface, especially during comparison or export.

Durable history, fetched records, proxy instances, full-detail instances and active animations are different counts. A world may retain every admitted entry without loading every historical TimeSensor and every mesh into the current browser scene. Node budgets and streaming policies need measurements of the actual working set.

Capacity follows bytes. Multiplying a document count by a per-shard patch count gives a count ceiling, not a demonstrated capacity. The serialized byte cap, witnesses, metadata and escaping can bind first. A million-entry skyline needs a measured load experiment before it becomes a performance claim.

What the backend actually measured.

reports/store-scaling.json records real 10- and 100-entry runs through the fragment gate, pinned XSD/semantic validator and SQLite transactions. The authored tier-3 workload used no mock witnesses, no admission bypass and zero model calls.

One shared Linux x86-64 runtime, CPython 3.12.14, one process and one writer. Append time includes the method’s return-time world read; caller snapshot/detail reads and checkpoint exports are outside it. The first append included cold schema/validator initialization and took 1,591.718 ms. These are local backend measurements, not GPU, browser, cloud, network or concurrent-author results.

1,000 entries: not run. The runner projected 154.386 s from the measured warm trend, above its configured 90 s stop rule. That is an explicit budgeting estimate, not a measured 1,000-entry result or a validated scaling law.

Optimize the growing work, not the caption.

Code inspection finds repeated full-payload scans and decoding in snapshots, placement reconstruction and world summaries. The measured early warm mean was 16.749 ms, versus 39.913 ms late in the 100-entry run; a function-level profile has not isolated the exact share of each cost. The next useful change is compact transactional head/cell-top/recent-cell indexes and bounded viewport reads, with those indexes checked against verified history. Repeated immutable instrument manifests can be stored once by content digest, provided exports include every referenced object. Version that change; preserve old entries and hashes.

The current local configuration caps durable entries at 10,000 and the fetched view window at 512. These are declared policy limits, not measured capacities or performance promises. The source notes proposed much larger capacity and streaming targets; those remain design hypotheses, not fresh measurements. Read fresh timings only with their device, browser, renderer and scene size attached.

09 / Take the world out of its page

An export earns trust
when it opens alone.

  1. Export the history as JSON.Retain the complete declared record, canonicalization version, payload identities and tail digest. Treat unknown or unrun evidence as unknown, not zero.
  2. Verify against the expected checkpoint.Recompute entry and previous-link identities, replay the deterministic plan and inspect candidate/evidence bindings. Preserve the first mismatch as a diagnostic.
  3. Export the whole X3D world.The exported scene should carry the admitted patch content and deterministic placement. Keep application decoration, view proxies and historical content clearly distinguished.
  4. Open the exported X3D without the application.A standalone load is a different check from seeing the world inside its maker. Check geometry, materials, motion, declarations and framing on the actual standalone file.

Root README.md gives the current launch and export commands. VALIDATION.md records which checks were actually executed. A successful JSON replay does not establish visual parity; a successful preview does not establish that the JSON record is complete. They are complementary observations.

Reproducibility needs a named boundary.

A deterministic planner maps declared state to a plan. A deterministic generator maps its declared seed, recipe, tier and version to a proposal. A validator maps exact candidate bytes to findings under pinned code and schema. These are useful narrower claims. They do not imply pixel-identical output across browsers, machines or renderer versions.

The guide is self-contained HTML with no external scripts, fonts or image assets. Its source links are optional reading. The interactive world and its renderer live in the companion project.

10 / Six experiments, from first look to protocol work

Predict a result.
Change one thing.
Keep the counterexample.

Watch a layer arrive.

Read the current head, grow one patch and inspect its placement and source label. Explain what the generator chose and what the world planner chose.

Keep: previous head, new sequence, cell/layer, recipe and admission status.

Compare two ambitions.

Generate two authored tiers. Compare the structural metrics with the silhouette and your own preference. A higher complexity number may not be your preferred result.

Keep: metrics, candidate identities and a separate human preference statement.

Revisit an earlier world.

Scrub to an earlier retained prefix, then return to the current head. Check that viewing history did not mutate it. Verify the chain and retain its checkpoint.

Keep: viewed head, current head and verification outcome.

Break a copy, not history.

Export JSON and alter one payload field in a separate copy. Verify it against the retained checkpoint. Distinguish a digest mismatch from malformed input and from a validator error.

Keep: the smallest changed field and the exact refusal diagnostic.

Make two plans from one head.

Use the supplied protocol tests or two author clients to submit work planned against the same head. Require one successor and an explicit stale-head outcome for the other.

Keep: expected head, committed head, both outcomes and proof that history did not branch silently.

Open the export alone.

Load a whole-world X3D export outside the application. Compare it with the chosen live head. Name any different camera, omitted proxy, unmeasured animation phase or unsupported feature.

Keep: exported file digest, runtime/version, head, view conditions and observed differences.

Tests should include the repaired twin. A negative input that fails for a missing dependency rather than its intended defect has not demonstrated the gate's rule. The instrument must be healthy before its red results are counted as successful controls.

The reusable unit is a scoped rule with an observable symptom, a minimal failing specimen, a repaired twin and a stable diagnostic. Its reach is no broader than what the test and reference can see. That is more valuable to the Loom than a large untested universal rule.

Three different records: the local app shows a result; the project validates its implementation; the fold-back patch carries a portable lesson. A lesson is not upstream merely because a local file calls it an integration. The delivered patch is for review and application; no external repository was modified or published.

13 / Read the source of the rules

A named instrument
makes a claim inspectable.

This guide follows the supplied Accretion notes and the current repository snapshots read for the reference build. It does not turn archived prices, private-host test counts or model names into fresh measurements.

  1. 01
    The X3D Loom definition, pinned commit

    Laws, roles, grades, profiles, scope, exact-candidate binding and the distinction between a witness and acceptance.

  2. 02
    Loom acceptance code

    A closed required set of current-candidate witness records, with status, grade, coverage and evidence checks.

  3. 03
    Loom receipt code

    Accepted-artifact records and their unsigned integrity scope. Similar-looking application JSON is not automatically this contract.

  4. 04

  5. 05

  6. 06
    X_ITE project

    The reference bundles X_ITE 16.6.0. That pin is separate from the 16.7.1 version named by the older build note; neither is called the newest release here.
